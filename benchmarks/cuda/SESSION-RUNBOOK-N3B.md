# CUDA session N3 stage B runbook: what the host issue time is made of (levels L0 to L5; RTX 5090)

Predictions, design and stop rules: `docs/CUDA-N3B-EXPERIMENT-RECORD.md` (committed in d2d3a15 before any stage B code). Harness: `benchmarks/cuda/overlap_arena.py` (the stage A file with levels and the `P0L` arm); the bookkeeping at every level equals the independent reference on the real trace (`chain2` and the counts, gate (a2)). The S1, S2, V1, N2, B1, B2 and N3 runbooks apply for the provider, key, private ssh config, cost log and teardown; `SESSION-RUNBOOK-N3.md` has the trace copy; this file lists what differs. **Nothing here starts an instance.** Hamed creates it when the agent says it is ready (about seven minutes to initialize) and says go for the named live instance; the agent runs over SSH only for that one instance and never runs sudo. Cap: **1 GPU-hour** from Ready, and every run of this session passes an explicit `--max-seconds` below what is left of it.

## Steps

1. Pack from a clean commit on the Mac (`bash benchmarks/cuda/pack.sh`, REVISION `dirty=0`); upload and unpack as in N3; copy the 11 MB trace to `~/cachalot-cuda/n3-trace.npz`.
2. **First check the instance**, before anything else: `nvidia-smi` must show the GPU and the driver (a VM with the packages but no loaded module is replaced by Hamed from the console: loading it needs root), and `getent hosts pypi.org` must resolve (a VM with no outbound network is rebooted from the console: the S2 and N3 fault). Then `check`, `setup`, `doctor`, `smoke` (all clean).
3. **`bash benchmarks/cuda/session.sh n3bsmoke`**: group `p17`, 40 decode tokens, C = 1.0 ms, levels `L0`, `L3`, `L4`, `L5` (14 cells). **This is the first GPU run of the new code**: the `P0L` arm, the pre-built views, the bare level's reduced events, the CUDA-graph capture and its calibration. Read every gate: `event_hash`, `determinism`, `counts`, `chain2`, `readback`, `calibration`, `drift`, `closure`, `sanity` all true, no failed cell, not truncated. `L5` reporting `graph_unavailable` (capture failed, or the replay time is more than 5 % from C) is a valid outcome, not a failure; look at `raw-samples.json` `graph` for the reason.
4. Only if the smoke is clean: `MAXS=1200 bash benchmarks/cuda/session.sh n3bfull` (43 cells; the estimate is 12 to 18 minutes; `MAXS` is the explicit cap in seconds, default 1500). A truncated run is reported as truncated.
5. Copy back with `results`; score by **field name**. Key fields: per cell `wall_ms_token`, `host_issue_ms_token`, `host_gap_ms_token` (`L0` to `L3` only), `compute_stall_ms_token`, `closure_share` (`L0` to `L3`), `demand_misses_per_token`, `prefetch_loads_per_token`, `bookkeeping_chain2`; per (level, C) `E_D`, `E_O`, `E_P0`, `E_P0L`, `E_P40`, `H_*`, `H_*_vs_L0_E_D` (levels without a `D` arm), `drift`, `floor_ms`, `compute_busy_ratio_*`, `per_copy_ms_c`; and the first cell's `source_copy_ms_*` and `source_records_slow_share` (the instance's population). The registered predictions B-P1 to B-P11 are scored from these; B-P1 to B-P3 are differences of `host_gap_ms_token` of the `O` arm between consecutive levels.

## What the gates mean here

As N3, plus `chain2`: from level 2 the timed bookkeeping has no event hash, so its rolling integer over every demand miss and prefetch load (token, layer, expert, slot) is compared with the untimed reference pass of the same cell; a mismatch means the lean path chose a different slot or a different victim and the cell is not a valid replicate. `closure` applies to `L0` to `L3` only (levels 4 and 5 record no per-layer events).

## Stop rules

Stop on a failed cell, a false gate, truncation, an event-hash or `chain2` mismatch (a harness bug: fix on the Mac), a drift flag on the first `N` pair, or 80 % of the cap before the first scored cell. A defect found on the instance is fixed on the Mac. Housekeeping stands (delete the S1, S2, V1, N2, B1, B2 and N3 ssh configs, known_hosts files and the key; the N3 billed hours).
