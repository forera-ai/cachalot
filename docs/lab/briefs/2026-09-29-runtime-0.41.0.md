# Codex brief — runtime 0.41.0 (2026-09-29)

Tracks Cachalot runtime **0.41.0** (HANDOFF section 18.22). Two MiniMax memory knobs, both on by default and
bit-identical; no endpoint, stats field or log line changed. The `mlx=` field of `[request]` lines now ends at
~0.2 GiB of buffer cache after a MiniMax reply instead of 2.0 (same format).

## 1. Contract-file edits

### `runtime-contract/knobs.yaml`

```yaml
- key: CACHALOT_MINIMAX_DECODE_CACHE_GIB
  kind: env
  families: [minimax-m3]
  type: float
  default: {minimax-m3: 0.25}
  range: [-1, 8]
  group: memory
  effect: speed-only
  restart_required: true
  stability: shipped
  since: 0.41.0
  summary: >-
    MLX's buffer-cache cap while a reply decodes (prefill keeps 2 GiB). 0.25 keeps all processes' GPU memory under
    the working set; a negative value keeps 2 GiB (short follow-up prefills then ran 3-5x slower in a third of turns).
  doc: HANDOFF 18.22 item 3
- key: CACHALOT_MINIMAX_SPILL_BLOCKS
  kind: env
  families: [minimax-m3]
  type: bool
  default: {minimax-m3: 1}
  group: memory
  effect: speed-only
  restart_required: true
  stability: shipped
  since: 0.41.0
  summary: >-
    A system-block snapshot saved on disk leaves memory after each request (2.4 GiB back to the expert cache in a
    Hermes session) and reloads in ~0.4 s when a new conversation starts with it. 0 keeps it in memory.
  doc: HANDOFF 18.22 item 2
```

### `runtime-contract/compat.yaml`

- `minimax_decode_cache_cap: ">=0.41.0"`, `minimax_spill_blocks: ">=0.41.0"`.

## 2. UI changes

- **Profiles → Memory (MiniMax), advanced:** "Decode buffer cache (GiB)" (0.25; "keep prefill's" writes -1) and
  "Keep system blocks in memory" (off; on writes `CACHALOT_MINIMAX_SPILL_BLOCKS=0`). Both labelled "speed only,
  same outputs".
- **Cockpit memory panel:** nothing new to parse; if it plots the `mlx=` cache figure, expect ~0.2 GiB after replies.
